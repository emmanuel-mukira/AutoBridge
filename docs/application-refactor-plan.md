# Application cleanup and refactor plan

Audit date: 15 October 2026. This is a read-only source audit and implementation plan; no copied application has been built or run.

## Current state and cleanup boundary

- `apps/frontend/` is a React/Vite application (`src/main.tsx`, `src/app/router.tsx`) with local `package.json`, `package-lock.json`, Vite and TypeScript configs. Routes cover login, signup, password recovery, dashboard, customers, leads, quotations, call planner, interactions, audit logs and administration. Its API client is `src/lib/http.ts`; auth still uses `src/app/store.ts` and `src/app/auth/autheliaService.ts`.
- `apps/crm-api/` is Express/TypeScript (`src/index.ts`, `src/app.ts`) with local manifest, npm lockfile and TypeScript config. Routes, controllers, services and Zod schemas cover customers, contacts, leads, quotations, interactions, call plans, users, audit logs and analytics. `src/middleware/auth.ts` trusts Authelia `Remote-*` headers; `src/app.ts` relies on Traefik/header handling and a local Authelia proxy. `src/index.ts` starts a Timescale sync job. `src/lib/analyticsDb.ts`, event controllers and analytics service use the separate analytics database. Redis appears in session cleanup comments; `pino-loki` remains a package dependency. No local Grafana or Infisical service configuration was found.
- Prisma source is `apps/crm-api/prisma/schema.prisma` plus `prisma/models/{auth,customers,leads-and-predictions,sales-activity}.prisma`; old migrations are in `prisma/migrations/`. The schema targets `public`, `auth` and `crm` and includes generator fields, prediction records and company/user/history relationships. `prisma/seed.ts` belongs to the old schema. These are **not** generated files.
- Both Dockerfiles copy missing root pnpm workspace files and `packages/shared-types`; the repo has no root Node manifest/workspace or shared package. They cannot currently build from their own application roots. Search of TypeScript imports found no confirmed source import crossing an application boundary; `@/` resolves to frontend `src`. The Dockerfiles and the seed script are the concrete old workspace references.
- No `apps/**/.env*`, `node_modules/`, `dist/`, `build/`, cache, generated Prisma client, temp or log files were found in this snapshot. No app files are tracked yet (`git ls-files apps` is empty); `git status` reports `?? apps/` plus pre-existing untracked docs. Preserve those user files. The prior report of malformed concatenated root ignore entries was a display artifact from printing multiple files together: `.gitignore` itself was intact. The root `/datasets/` ignore remains intentional; tracked model artifacts are unaffected. Recheck tracked and untracked env files before the first commit, without opening their values; rotate credentials if any were ever committed.

## Target layout and independent configuration

Keep `apps/frontend/`, `apps/crm-api/`, `models/automotive_v1/`, `docs/` and notebooks in this repository; add `services/ml-api/` only in Stage 6. Each app retains its own manifest, lockfile, scripts and deployment root. No pnpm workspace, shared package, Nx or Turborepo is indicated. Existing npm scripts provide frontend `npm ci`, `npm run build` and backend `npm ci`, `npm run build`, `npm run start`; verify them independently once source contracts are made coherent. The backend `tsconfig.json` includes `prisma.config.ts`, which is absent, and compiles `prisma/seed.ts`, so confirm actual emitted entry path before choosing the Render start command. Prisma package versions also differ (`@prisma/adapter-pg` 7.2 vs client/CLI 6.16), requiring version alignment before generation/build. Add explicit app-local Prisma generation/config only after selecting the fresh schema.

## Stages and completion checkpoints

1. **Safe cleanup.** Repair ignore rules, inventory secret paths, remove only approved obsolete deployment recipes and genuinely generated files if present, retain source/migrations for later decisions. Check `git status`, `git diff --check`, and verify both lockfiles and essential source/assets still exist. No install or build needed.
2. **Independent app setup.** Remove root-workspace assumptions from scripts/config, decide Prisma version/config and emitted entry path, supply sanitized env examples and Vercel SPA routing. Check each manifest/lockfile pair and run independent install/typecheck/build only when that application's imports are ready; record any legacy compile blockers without broad refactoring.
3. **Minimal local infrastructure.** Add one Docker Compose PostgreSQL service with a named volume, health check and environment-based credentials; document a local `DATABASE_URL` and keep it out of Git. Check Compose syntax/config without starting a container; then start only when ready for fresh schema work. Neon is production only.
4. **Backend auth and schema.** Specify company/user roles and password/session lifecycle; implement Express-managed, server-validated sessions with secure cookie settings, CSRF protection and a durable PostgreSQL session store suitable for Render. Replace trusted identity headers and Authelia user provisioning together; keep protected routes closed throughout. Remove Timescale startup/event dependencies after replacing required dashboard/history queries in PostgreSQL. Design new automotive Prisma models using company/user/customer/contact/opportunity/interactions/follow-up and prediction history requirements; create migrations only against a fresh database. Preserve tenant scoping, authorization, audit history and money/date precision. Check Prisma validation, migration on disposable local DB, unauthenticated/role/tenant failures, login/logout/session expiry and essential CRUD. Never migrate old data by assumption.
5. **Frontend workflows.** Keep shared UI controls, styling, layout, query layer and customer/contact components; replace Authelia login/session/logout and old API contracts first. Keep dashboard, customer and interaction surfaces but refactor their Timescale and generator data. Rename/refactor `pages/Leads.tsx` and `features/leads/` to opportunity/pipeline semantics after backend contracts exist; refactor `CallPlanner` for follow-ups. Review `Quotations`, admin roles, audit logs, signup/invite/recovery and old charts for product fit before removal. Add automotive product/category selection and prediction result/history views only against implemented APIs. Check route guards, loading/errors, mobile layout and core flows against a running backend; do not delete shared UI by filename alone.
6. **ML inference.** Build a small validated FastAPI endpoint loading the frozen primary and limited-history fallback joblib files plus `metadata.json`. Use `docs/automotive-model-decisions.md` and `docs/ibm-crm-feature-mapping.md` for the mapping; do not alter artifacts, notebooks or feature definitions. Require valid product hierarchy, route, amount/conversion provenance, artifact version and verified history state. Unknown history must not become code `0`; use the approved fallback only with its required inputs, otherwise return review-required. Express calls FastAPI server-side and persists version, source inputs, result and decision trail. Check real saved-artifact predictions, invalid category/history rejection, fallback routing and service failure handling. IBM compatibility is not Kenyan calibration.
7. **End-to-end and deployment preparation.** Exercise login through prediction and follow-up, cross-origin cookies/CORS, tenant isolation, migrations on disposable DB, frontend deep links and failure paths. Then verify Vercel/Render roots, environment names and Neon connection behavior. Do not deploy during this plan.

**First implementation checkpoint:** Stage 1 produces a clean inventory and ignore policy, with the obsolete Docker/nginx deployment files removed only after the Vercel SPA replacement is specified. It must leave all application source, Prisma schema/history, model artifacts and credentials intact for the later dependency-aware stages.
