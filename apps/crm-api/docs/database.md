# AutoBridge database and workflow

The active single-company PostgreSQL schema is `prisma/automotive/` (selected by `prisma.config.ts`). Its split model files and migrations are the source of truth. The old Lead, quotation and analytics modules are not mounted in the active API.

| Table | Purpose and key relationships |
| --- | --- |
| `User`, `Session` | `ADMIN` or `SALES_REP`; PostgreSQL-backed sessions belong to users. |
| `Client`, `Contact` | External B2B organization owned by a user; contacts belong to one client. Soft-deleted clients are hidden by the active API. |
| `ProductGroup`, `ProductSubgroup` | Controlled automotive/RV hierarchy; an opportunity selects a subgroup and derives its parent group. |
| `Opportunity` | Belongs to a client and owner; optional subgroup and route allow draft creation before scoring. Stores the original estimate separately from a Won sale's confirmed amount, currency, USD conversion snapshot and confirmation time. Pipeline `stage`, final `outcome` and `outcomeAt` remain separate. |
| `Interaction`, `FollowUp` | Client activity with an optional opportunity link; interactions record an actor and occurrence time; follow-ups record channel, owner, due date and optional completion. |
| `ClientRevenueSummary` | Evidence that the client's sales records are complete for a stated period, with the verified aggregate snapshot, currency, source, verification time and verifier. No qualifying row means unknown; a complete period whose confirmed Won sales sum to zero is verified zero. |
| `OpportunityPrediction` | Append-only model result with primary/fallback variant, model and adapter versions, input/conversion JSON snapshots, Won probability, optional explanation and prediction time. Primary requires a revenue summary; fallback has none. |
| `PredictionReview` | Separate human assessment/comment linked to prediction and reviewer. It does not set opportunity status or Won/Lost outcome. |

A client is created with a required owner, can be edited by its owner or an administrator, and is soft-deleted through `deletedAt`; its contacts remain stored but are hidden by the active API. Naming: `Client.businessName`, `Client.ownerId`, `Contact.clientId`, `Opportunity.estimatedAmount`, `Interaction.interactionType`, `ProductSubgroup.productGroupId`. Original money is decimal with an ISO currency code. Sales route is one of `FIELDS_SALES`, `OTHER`, `RESELLER`, `TELECOVERAGE`, `TELESALES`; the scoring adapter must map these to the exact IBM labels and convert the original amount to USD using a recorded rate/source/time. The ten supported subgroup/parent pairs come from `docs/ibm-crm-feature-mapping.md`; unknown revenue must never be coded as verified zero. The primary model uses five approved inputs, while the limited-history fallback omits revenue. Product and route fields may be absent until scoring is requested.

An opportunity starts `NEW`, can advance through `QUALIFYING`, `PROPOSAL`, `NEGOTIATION` and `CLOSED` (forward skips allowed), and cannot move backward or reopen. `CLOSED` requires `WON` or `LOST` plus `outcomeAt`; open stages require both to be null. Closing as Won also requires the actual sale amount and currency. The service records the original confirmed value and an exact USD conversion snapshot with its rate, source and observation time; the estimate is never treated as verified revenue. An authorized correction replaces that confirmed-sale snapshot without changing the commercial outcome. Predictions and reviews do not change this lifecycle.

Client sales history is calculated for an explicit `asOf` timestamp. The two-year window ends at that timestamp, excludes Lost, open, unconfirmed and future outcomes, and sums only confirmed Won values in USD. A qualifying `ClientRevenueSummary` attests that the underlying records cover the full window. The API returns `UNKNOWN` without that evidence, `VERIFIED_ZERO` when complete records sum to zero, and `VERIFIED_COMPLETE` for a positive total. Only the two verified states receive an IBM revenue band; unknown remains `null` and must use the limited-history path later. Recalculation from confirmed opportunities means a recorded correction is reflected without rewriting past opportunities.

Implemented endpoints: `/api/auth/*`, `/api/clients`, `/api/clients/owners`, `/api/clients/:id/sales-history`, `/api/clients/:id/revenue-coverage`, `/api/contacts`, `/api/opportunities`, `/api/opportunities/:id/stage`, `/api/opportunities/:id/confirmed-sale`, `/api/opportunities/:id/score`, `/api/opportunities/:id/predictions`, `/api/opportunities/products`, `/api/opportunities/owners`, `/api/interactions`, `/api/follow-ups` and `/api/analytics/overview`. Client, contact, opportunity and activity operations use session, CSRF, role and owner authorization. Administrators can assign a client to an active user; sales representatives see only themselves as an owner choice. A client with opportunities cannot be reassigned until those opportunities have an explicit transfer workflow, which prevents client and opportunity ownership from diverging. Opportunity create/edit stores the original decimal estimate and currency; listing supports search, client, owner, product, stage and route filters. Product groups and subgroups are read-only controlled data. The old `/api/customers`, `/api/customer-contacts` and `/api/leads` paths are not mounted.

Scoring is server-to-server. Express authorizes the opportunity, converts its estimate to raw USD, asks the sales-history service for evidence at the scoring timestamp, and selects `PRIMARY` for verified positive or verified-zero history and `LIMITED_HISTORY` only for unknown history. It then calls the internal FastAPI service with a five- or four-feature contract. A successful response creates an append-only `OpportunityPrediction`; failures create no row and never change stage or outcome. The JSON snapshots retain the requester, source opportunity values, exact model-ready features, revenue evidence, original currency and conversion provenance. Genuine Won-class Tree SHAP contributions, baseline, units and explainer metadata are saved in the prediction's existing nullable `explanation` field; older null explanations remain valid. Prediction history reports whether the latest saved features differ from current eligible inputs. Opportunity listing returns a batched latest-score summary and never runs inference. Human prediction review remains later work.

Interactions support authorized list/detail/create/edit/delete operations. They record the authenticated actor, and a linked opportunity must belong to the selected client. Sales representatives can read activity for clients they own and can edit or delete only interactions they recorded; administrators can manage all visible interactions. Filters cover client, opportunity, actor, type and occurrence dates.

Follow-ups support authorized list/detail/create/reschedule and completion operations. New follow-ups require a validated call, email, meeting, site-visit or other-follow-up channel. They are assigned to the active client owner, and a linked opportunity must belong to that client and owner. Sales representatives see only their assigned follow-ups for clients they own; administrators can view all follow-ups. Completion is idempotent and records `completedAt` separately from `dueAt`. Filters cover client, opportunity, owner, completion state and due dates.

`GET /api/analytics/overview` provides authenticated PostgreSQL operational reporting. Administrators can report across all authorized records or filter by owner; sales representatives are always restricted to their own clients, opportunities and assigned activity. Opportunity filters cover creation period, owner, stage, outcome and product group. The reporting period applies to `Opportunity.createdAt`, `Interaction.occurredAt`, `FollowUp.dueAt` for pending items and `FollowUp.completedAt` for completed items. Stage, outcome and product filters apply to opportunity panels; activity panels use the selected period and owner scope.

Total opportunities are scoped records; open means no final outcome; win rate is `Won / (Won + Lost)` and is `null` when no opportunities are resolved. Open pipeline value includes only opportunities without an outcome. Currency totals are grouped in PostgreSQL by stored currency, then converted with Prisma Decimal to a USD reporting basis using the documented illustrative KES rate. The response includes the rate, source and observation time, and the frontend applies the global USD/KES display preference. It is not a live exchange rate. Upcoming follow-ups are incomplete items from now through the reporting end; overdue items are incomplete and before now; completed items use their completion time. Follow-up attention lists open opportunities with no incomplete future follow-up. No dashboard value is a model probability.

From `apps/crm-api`, run `npm run dev`, then `npm run verify:foundation`, `npm run verify:opportunities`, `npm run verify:activities`, `npm run verify:analytics`, `npm run verify:sales-history` and `npm run verify:predictions` in another terminal. Prediction verification also requires the local ML API. Prisma checks remain `npx prisma validate`, `npx prisma generate`, `npx prisma migrate status` and `node scripts/verify-schema.mjs`. Verification scripts clean up their temporary rows; seed and schema checks require the ignored local development `.env`. Never run the development seed against production.
